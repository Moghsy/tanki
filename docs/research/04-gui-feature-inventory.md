# 04 - Anki desktop GUI feature inventory (for the "tanki" terminal client)

Source: Anki v26.08.1 at `/home/emard/projects/open-source/anki` (read-only). All paths below are relative to that repo unless absolute.
Scope: `qt/aqt/**`, `qt/aqt/forms/*.ui`, `ts/routes/**`, the menu/shortcut definitions, `qt/tools/genhooks_gui.py`, `pylib/tools/genhooks.py`, plus the proto/rslib files needed to decide "is the logic in Rust?".

This is a checklist, so breadth beats depth. Other researchers cover scheduler/reviewer internals, rendering, sync/import/export, browser/search and the editor in depth; those areas are listed here with entry points only.

## 0. Legend and method

**Logic location column ("Logic")**

| Code | Meaning |
|---|---|
| **R** | Logic is in the Rust backend (`rslib`), reachable via a protobuf RPC. A Rust TUI links `rslib` directly and gets it for free. |
| **R+ui** | Logic is in Rust but the form/validation/orchestration is Python/Svelte and must be rebuilt as TUI screens. |
| **P** | Logic lives in Python (`aqt`/`pylib`), not in Rust. Must be re-implemented in Rust (or dropped). |
| **T** | Logic lives in TypeScript/Svelte (the page computes or renders it itself). Must be re-implemented. |
| **Q** | Qt/WebEngine/OS-specific. No equivalent logic to port; needs a terminal substitute or is dropped. |

**Terminal-feasibility verdict**

| Verdict | Meaning |
|---|---|
| **trivial** | A list/prompt/toggle. Hours. |
| **doable** | Needs a non-trivial TUI screen or some glue, but no hard unknowns. Days. |
| **hard** | Large UI surface, or needs rich rendering (images, charts, WYSIWYG), or a big re-implementation of Python logic. Weeks, or degrade. |
| **impossible** | Physically needs a GUI toolkit/webview/JS engine. Substitute or drop. |

Line numbers are for the checked-out tree. "ftl" strings were not all resolved to English; labels below are paraphrased from `tr.*` keys (e.g. `tr.preferences_reduce_motion`).

**Global architecture facts that drive every verdict**

1. The main window is a QMainWindow with **three QWebEngine views** (top toolbar, main area, bottom bar). The deck list, overview, reviewer and legacy stats are **HTML pages generated by Python strings** (`deckbrowser.py:_renderPage`, `overview.py:_table`, `reviewer.py`), styled with CSS in `qt/aqt/data/web/css`. Only the modern dialogs are SvelteKit pages (`ts/routes/*`, section 20). None of the page *HTML* is reusable by a TUI; the *data* behind it nearly always is (RPCs).
2. The backend exposes ~270 RPCs (`proto/anki/*.proto`: scheduler 39, frontend 26 (UI-only), decks 24, notetypes 19, card_rendering 17, collection 16, notes 14, tags 11, config 11, import_export 11, deck_config 10, media 10, search 9, sync 9, image_occlusion 6, ...). Nearly everything "collection-shaped" is R.
3. Everything about **profiles, preferences-not-in-collection, windows, add-ons, TTS/audio playback, LaTeX image generation, legacy stats, and the update checker UI** is Python (P/Q).
4. Python-side concurrency is `CollectionOp`/`QueryOp` (`qt/aqt/operations/__init__.py`) wrapping backend calls; each op returns `OpChanges` flags that drive screen refresh (`main.py:on_operation_did_execute` 853). A TUI should copy this pattern (an `OpChanges`-driven refresh).
5. Anki is **modal-dialog heavy and mouse-first**; the keyboard layer is a thin overlay of single-key shortcuts (section 22).

## 2. Profile manager (global and per-profile preferences)

## 3. Main window, state machine, menus, toolbar

`AnkiQt` (`main.py:169`). States (`MainWindowState`, line 92): `startup`, `profileManager`, `deckBrowser`, `overview`, `review`, `resetRequired` (legacy no-op). Transitions via `moveToState` (771), which calls `_<old>Cleanup`, clears per-state shortcuts, then `_<new>State`. Per-state shortcuts are installed with `setStateShortcuts` (1230). The refresh model: each screen implements `op_executed(changes, handler, focused)` + `refresh_if_needed()`; when the window is not focused the web view is faded to 30% opacity (`fade_out_webview` 888).

## 21. gui_hooks and the add-on API surface

* `qt/tools/genhooks_gui.py` defines **150 GUI hooks** (generated to `aqt/gui_hooks.py`), `pylib/tools/genhooks.py` **17 core hooks** (`card_odue_was_invalid, schema_will_change, notes_will_be_deleted, note_will_be_added, media_files_did_export, legacy_export_progress, exporters_list_created, media_file_filter, field_filter, note_will_flush, card_will_flush, card_did_render, importing_importers, deck_added, note_type_added, sync_stage_did_change, sync_progress_did_change`).
* Hooks are named `<noun>_will_<verb>` / `_did_<verb>`, covering: overview/reviewer lifecycle (rendering, answer buttons, context menu, compare answer, answer card, suspend/bury, audio), deck browser, deck options/dconf, filtered deck, browser (menus, context menus, columns, search, row fetch, sidebar tree), previewer, main window state/operations/profile/sync/backup/themes, toolbar HTML injection, webview (JS message, content, context menu), add-cards, editor (init/shortcuts/buttons/focus/paste/mime/munge html/load note), tag editor, av player, add-ons dialog/config editor, models/fields dialogs, stats, empty cards, media check, exporter, flags, undo.
* Add-ons also freely import `aqt`, `anki`, `PyQt6`, monkey-patch, add menu items (`mw.form.menuTools`), registration of notetypes (`stdmodels.models`), exporters, importers, `mw.addonManager`, `mw.progress`, `CollectionOp`, `webview_will_set_content` (inject JS/CSS), etc.
* Config JSON per add-on + `config.schema.json` validation; `user_files/` preserved across upgrades; AnkiWeb add-on IDs and update protocol.

**Terminal implication:** zero binary compatibility; the whole add-on ecosystem is out. Cheap, high-value substitutes: (1) AnkiConnect-compatible JSON API (many users depend on it for Yomitan/etc.), (2) a native hook/plugin mechanism (e.g. scripting with `mlua`/`rhai`/external-process JSON-RPC) exposing a few dozen events (answer card, note add, sync done, state change), (3) configurable keybindings (Anki has none except answer keys!), (4) ability to import/export `.apkg` so add-on-created content is still readable.

### 25.3 Surprises / easy to forget
1. `prefs21.db` stores **Python pickles**; profile and global prefs are not portable to a non-Python client. AnkiWeb `hkey` lives there.
2. The sync **server** is built into the Anki binary (`--syncserver`) - free to expose from a Rust TUI.
3. LaTeX image generation, legacy stats, Mnemosyne import, add-ons, TTS and audio playback are the main **Python-only logic** that has no Rust implementation; LaTeX (`pylib/anki/latex.py`) is just two subprocess commands and is easy to port.
4. Shift-key modifiers silently switch implementations (safe mode at launch, old/new editor, old/new stats, old/new deck options, select-without-open deck rows).
5. Day rollover handling and the **timebox** prompt are easy to forget in a long-running TUI.
6. The **schema-change confirmation** ("requires full upload to AnkiWeb") fires for many note-type edits.
7. Deck options has **per-deck "Today only" and "This deck" overrides** for daily limits, parent-limit semantics, and **Easy Days**.
8. `deleted.txt` log of deleted notes is written by the GUI, not the backend.
9. Reviewer answer keys are the only user-configurable shortcuts; undo is **backend-side and covers answers**.
10. Three `.ui` forms are orphaned (browseropts, changemodel, setgroup).
11. The deck description supports Markdown (flag `md`) and raw HTML; filtered decks show a fixed text instead.
12. `DeckBrowser` shows a "scheduler update required" banner for collections not on v3; upgrade triggers a full sync.
